Существующие проблемные места:

1. Клиенты жалуются на долгое ожидание заказов, хотя производственные мощности не нагружены.
2. Заказы сделанные через MES API тоже выполняются слишком долго.
3. Есть жалобы на неполученные заказы.
4. Жалобы пользователей на UI MES - долго прогружается. Пагинация не помогла.
5. Проблемы с планированием спринтов\релизов, что сильно задерживает поставку обновлений.

Потенциальные проблемные места:
1. Так как проблемы с долгим ожиданием появились после значительного увеличения заказов, какая-то из систем (или несколько) не справляется с нагрузкой.
2. Проблемы с надёжностью. Возможны "потери" заказов в системе. Когда в одной системе заказ есть, а в другую он не попал.
3. Низкий уровень наблюдаемости системы. Пользователи первые сообщают о проблемах.
4. В данный момент система не масштабируема.

Инициативы:
    1. Настроить мониторинг и визуализацию мониторинга всех систем.
    Результат: Можно оценивать в моменте и в динамике нагрузку приложений и отслеживать узкие места.

    2. Вывести логирование в централизованную систему.
    Результат: Ускорение работ по анализу проблем.

    3. Настроить трассировку заказов
    Результат: Видеть полный цикл обработки заказа, чтобы понимать где заказ провисает.

    4. Развернуть микросервисную архитектуру. 
    Результат: Масштабируемость системы

    5. Разбить SPA приложение MES на микрофронтенды.
    Результат: повышение отклика UI приложения.

    6. Выделить микросервис нотификации об изменении статусов. Как вариант, добавить брокер куда будут поступать статусы.
    Результат: Корректное отображение статусов для клиентов. Повышение информативности о статусе заказов во всех системах.

    7. Автоматизировать пайплан разработки, тестирования и внедрения CI\CD.
    Результат: ускорение разработки, тестирования и внедрения. Увеличение скорости поставок.

    8. Введение кэширования и реплик для БД, по результатам логирования\трассировки\мониторинга.
    Результат: повышение быстродействия и отказоустойчивости системы

    9. Автоматизация тестирования. Регресс-сценарии. Расширение команды тестирования.
    Результат: увеличение скорости поставок, повышение качества поставок.

    10. Ввести нагрузочное тестирование.
    Результат: можно внедрить новые решения для балансировки нагрузки, до того как сервисы будут перегружены.

В целевой архитектуре через полгода:
Логирование, мониторинг, трассировка, реплики БД, SPA с микрофронтендами.

В первую очередь логирование и мониторинг.

        Для базы данных это будут реплики\кэширование, может быть шардирование.
        Для UI микрофронтенды
        И т.д. в зависимости от результатов анализа, возможно это будет новое решение, не из списка выше.

        Необходимо настроить трассировку, чтобы иметь более полное представление о том, куда двигаться дальше.
