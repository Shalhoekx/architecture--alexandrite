Мотивация
Сейчас, при возникновении каких-либо проблем с ИТ сервисами Александрита, компания узнаёт от них только от пользователей.
Такой подход имеет ряд серьёзных проблем:
    - Несвоевременность. К тому времени как начнут поступать отзывы, проблема может усугубиться и нанести больше ущерба. И количество "пострадавших" клиентов будет больше.
    Что усложнит исправление проблемы - нужно будет не только устранить проблему, но и потом исправить\откатить ошибки. И чем больше накопится ошибок, тем это будет сложнее (а иногда попросту невозможно).
    - Отказ системы. Перегрузка системы редко бывает мгновенной. И система имеет запас прочности. Но если очень долго не реагировать на перегруженную систему, это может привести к её остановке и отказу.
    - Прогнозируемость. В продуктив выкатили новую версию приложения. При пиковой нагрузке новая версия приложения не справилась и начала тормозить.
    Мониторинг уже при запуске приложения, позволить сравнить метрики новой версии, с метриками старой. И если приложение сразу покажет себя плохо, его можно будет откатить или сделать хот-фикс.
    - Негативный опыт. По итогу, если клиенты узнают о проблемах раньше, чем компания - это не только увеличивает технические трудности для компании. Но ещё и несёт репутационные издержки и приносит негативный клиентский опыт.
    Компания может терять клиентов (и несколько контрактов компания уже потеряла).

Выбор подхода к мониторингу

Предлагаю использовать подход к мониторингу от Google: четыре золотых сигнала:
    - Задержка
    - Трафик
    - Ошибки
    - Насыщенность 

Для сервиса MES необходимо ещё добавить метрики из подхода USE (Утилизация, Насыщенность, Ошибки). Так как сервис выполняет обработку 3Д моделей и его работа очень требовательна к ресурсам и обработка занимает длительное время.
    - Утилизация.



Метрики для отслеживания
    - Number of dead-letter-exchange letters in RabbitMQ
    Метрика проблемных сообщений в очереди RabbitMQ. Отображает кол-во сообщений в очереди, которые не могут быть доставлены по каким-либо причинам (ошибка, переполнение).

    - Number of message in flight in RabbitMQ
    Метрика количества передаваемых сообщений ("в пути").

    - Number of requests (RPS) for internet shop API
    - Number of requests (RPS) for CRM API
    - Number of requests (RPS) for MES API
    Метрики количества запросов к API. Метрика востребованности ресурса, одна из ключевых для прогнозирования, так как имеет очень сильное влияние на все остальные.

    - CPU % for shop API
    - CPU % for CRM API
    - CPU % for MES API
    Метрики ресурсов ЦПУ для каждого сервиса. Позволяют в моменте отследить перегруз по вычислительным ресурсам системы.

    - Memory Utilisation for shop API
    - Memory Utilisation for CRM API
    - Memory Utilisation for MES API
    - Memory Utilisation for shop db instance
    - Memory Utilisation for MES db instance
    Метрики утилизация ОЗУ для сервисов. При большой утилизации, начинает повышать нагрузку на ЦПУ и диски и снижает скорость обработки. При критичной утилизации начнёт происходить неуправляемый отказ приложений.

    - Response time (latency) for shop API
    - Response time (latency) for CRM API
    - Response time (latency) for MES API
    Метрики "скорости" ответа от API. 

    - Number of HTTP 500 for shop API
    - Number of HTTP 500 for CRM API
    - Number of HTTP 500 for MES API
    Метрики внутренних ошибок API. В первую очередь сигнализируют об ошибках в API, но также могут вызываться при проблемах с утилизацией ресурсов.


План действий
    Встреча с бизнесом (не ИТ отделами) и определение проблем.
    Формирование команды или выделение специалистов (ресурса) на внедрение.
    На основе выделенных проблем, корректируем список метрик.
    Выбираем программное решение, подходящее под наши запросы\возможности.
    Определяем ролевую модель и способы информирования.
    Выделение инфраструктуры для нового решения.
    Развёртывание (Prometheus, Grafana).
    Поэтапно настраиваем
         сбор метрик
         дашборды
         алерты
    Запускаем MVP мониторинг
    Проводим обучение
    Дополняем метрики.

Показатели насыщенности
    В зависимости от ПО и используемых ОС могут сильно отличаться.
    Необходимо использовать рекомендации от разработчиков и поставщиков ПО.
    Например для C# критичной метрикой является утилизация RAM. 
        При 80% необходимо слать алерты и брать сервер на контроль, так как приложение может замедлить свою работу.
        При 90% уже начнётся отказ приложений.
